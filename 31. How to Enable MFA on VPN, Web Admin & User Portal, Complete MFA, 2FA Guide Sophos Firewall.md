# Sophos Firewall: Configuring Multi-Factor Authentication (MFA) for Administrators and VPN Users

> [!IMPORTANT]
> This guide explains how to configure and apply **Multi-Factor Authentication (MFA)** in Sophos Firewall for administrators, user portals, VPN portals, and VPN users. It also covers real-world deployment scenarios, common authentication problems, MFA enrollment, token management, and recommended security practices.

---

## 📋 Overview

**Multi-Factor Authentication (MFA)** adds an additional layer of security beyond a username and password.

If a user's password is:

* Compromised
* Leaked
* Shared with another person
* Discovered through another source
* Obtained through phishing or another credential-theft attack

the password alone should not be sufficient to access the organization's systems.

With MFA enabled, the user must provide an additional authentication factor, typically a **One-Time Password (OTP)** generated by an authenticator application.

This additional layer significantly reduces the risk of unauthorized access.

### Basic Authentication Model

```text
Username
    +
Password
    +
MFA / OTP
    =
Authenticated User
```

---

# 🎯 Why Is MFA Important?

Organizations should consider MFA an essential security control for protecting administrative interfaces, remote-access services, and other sensitive systems.

Consider the following scenario:

1. A user's password is compromised.
2. An attacker obtains the username and password.
3. The attacker attempts to access the organization's VPN.
4. MFA is enabled.
5. The attacker is prompted for an OTP.
6. The attacker does not have access to the user's authenticator application.
7. Authentication fails.

Without MFA:

```text
Compromised Username + Password
              ↓
       Authentication
              ↓
       Potential Access
```

With MFA:

```text
Compromised Username + Password
              ↓
          MFA Prompt
              ↓
      No Valid OTP Available
              ↓
      Authentication Denied
```

> [!NOTE]
> MFA does not make a compromised password harmless, but it prevents the password alone from being sufficient for authentication.

MFA is particularly important for users who work remotely because VPN credentials can provide access to corporate resources from outside the organization's physical network.

---

# 🌎 Real-World Scenario 1: Compromised VPN Password

Consider a company named **Contoso Technologies**.

The environment contains:

```text
Employees:          500
Remote Users:       300
VPN Users:          250
IT Administrators:    5
Firewall:        Sophos Firewall
```

One employee, **Rahul**, uses the same password on multiple websites.

One of those websites experiences a security breach, and Rahul's password is exposed.

The attacker now has:

```text
Username: rahul@contoso.com
Password: ********
```

The attacker attempts to connect to the company's VPN.

### Without MFA

```text
Attacker
   ↓
Username + Password
   ↓
Authentication Successful
   ↓
VPN Access
```

### With MFA

```text
Attacker
   ↓
Username + Password
   ↓
MFA Challenge
   ↓
OTP Required
   ↓
Attacker Does Not Have Authenticator
   ↓
Authentication Failed
```

### Result

The compromised password is no longer sufficient to complete authentication.

> [!TIP]
> Remote-access VPN should generally be considered a high-priority service for MFA because it provides access from outside the organization's trusted network.

# 🔐 Where Should MFA Be Enabled?

MFA should be applied according to the organization's security requirements.

Typical locations include:

| Access Type                    | MFA Recommendation | Purpose                                                |
| ------------------------------ | ------------------ | ------------------------------------------------------ |
| Firewall Administrator Account | **Required**       | Protects administrative access to the firewall         |
| User Portal                    | **Recommended**    | Protects user self-service access                      |
| VPN Portal                     | **Recommended**    | Protects VPN configuration and portal access           |
| Remote-Access VPN              | **Required**       | Protects remote access to corporate resources          |
| Privileged User Accounts       | **Required**       | Provides additional protection for high-value accounts |

---

## 🏢 Small Organizations

Some small organizations may not enforce MFA consistently at the user level.

However, administrative accounts should still be protected with MFA.

At a minimum, protect:

* Firewall administrators
* VPN users
* Privileged accounts
* Remote-access services

---

## 🏢 Mid-Size and Large Organizations

For mid-size and large organizations, MFA should generally be enforced for:

* Remote users
* VPN users
* Privileged users
* Firewall administrators
* Users accessing sensitive corporate resources

Remote users represent a particularly important security consideration because they can access corporate services from outside the organization's controlled network.

# 👤 Administrator MFA

If you need to enable MFA for the **Sophos Firewall administrator account**, the administrator MFA configuration is separate from the general user MFA configuration.

Navigate to:

```text
Administration → Device Access
```

Locate the appropriate administrator access settings and enable MFA for the administrative account.

After MFA is enabled, the administrator will be required to provide an OTP during authentication.

> [!IMPORTANT]
> Administrator MFA should be enabled before deploying MFA broadly to users. Administrative access is one of the highest-priority areas to protect.

---

Without MFA:

```text
Administrator
      ↓
Username
      ↓

      ↓
```

If the administrator password is compromised, the attacker may gain highly privileged access.

With MFA:

```text
Administrator
      ↓

      ↓

      ↓
Firewall Administration
```

The attacker now requires the additional authentication factor.

> [!CAUTION]
> A compromised firewall administrator account can have significantly greater impact than a compromised standard user account. Protect administrator accounts with strong authentication controls.

# 👥 User MFA Configuration

For regular users, navigate to the MFA configuration under the authentication settings.

The general workflow is:

```text
Dashboard
   ↓
Authentication
   ↓
Multi-Factor Authentication
   ↓
MFA Settings
```

The **Multi-Factor Authentication (MFA) Settings** section controls how MFA is applied to users and supported access services.

---

# 🎯 Select Which Users Require MFA

Depending on your organization's requirements, MFA can be applied broadly or selectively.

## Option 1 — All Users

Select the option to enable MFA for all applicable users.

This is appropriate when organizational policy requires MFA for every user.

```text
500 Users
   ↓
MFA Enabled
```

## Option 2 — Specific Users

If MFA needs to be introduced gradually, or only certain accounts require MFA, select the appropriate users individually.

For example:

* VPN users
* IT administrators
* Privileged users
* Remote employees
* Users accessing sensitive systems

```text
VPN Users
Privileged Users
IT Administrators
Remote Employees
       ↓
      MFA
```

After selecting the required users, apply the configuration.

# 🌎 Real-World Scenario 3: All Users vs. Selected Users

Suppose the organization has the following users:

| User    | Department | VPN Required | MFA |
| ------- | ---------- | -----------: | --: |
| Rahul   | Finance    |          Yes |   ✅ |
| Priya   | HR         |           No |   ✅ |
| Amit    | IT         |          Yes |   ✅ |
| John    | Sales      |          Yes |   ✅ |
| Guest01 | Guest      |           No |   ❌ |

This could represent a phased MFA deployment.

However, for mature environments, MFA should generally be standardized across users rather than being treated as an exception-based security control.

# 🔑 Generate the OTP Token

The MFA configuration includes an option to generate an OTP token during the user's next sign-in.

The purpose of this option is to initiate the user's MFA enrollment process.

The general workflow is:

1. Enable MFA for the required user.
2. Configure token generation for the next sign-in.
3. Have the user authenticate through the appropriate portal.
4. Register the MFA token using an authenticator application.
5. The authenticator application generates time-based OTPs.
6. The user enters the OTP when prompted during subsequent authentication.

---

# ⚠️ Important Deployment Consideration

One of the most important considerations when enabling MFA is **user communication and enrollment planning**.

Consider an organization with **500 users**.

If all 500 users are working remotely and MFA is enabled without prior notification or enrollment instructions, users may suddenly be unable to authenticate.

The result could be:

* VPN authentication failures
* Increased help-desk tickets
* Users repeatedly entering incorrect passwords
* Confusion about whether the username or password is incorrect
* Remote users being unable to access corporate resources

> [!WARNING]
> Do not enable MFA for a large remote user population without first communicating the change and providing enrollment instructions.

# 🖥️ Understanding the Sophos Firewall Portals

Sophos Firewall provides different portals for different purposes.

Understanding the difference between these portals is important when configuring MFA.

---

## 🌐 Captive Portal

The **Captive Portal** is used to authenticate users before they receive network or internet access.

A typical user experience is:

```text
Connect to Network
      ↓
Captive Portal
      ↓
Enter Username and Password
      ↓
Authenticate
      ↓
Internet / Network Access
```

---

## 👤 User Portal

The **User Portal** provides users with access to user-specific information and services.

Depending on the configuration, users may be able to view information such as:

* Internet usage statistics
* Usage quota
* Applicable web policies
* Department-related information
* Personal settings
* Download options
* VPN-related resources
* Other services exposed by the organization

The User Portal is therefore an important location to consider when implementing MFA.

---

## 🛠️ Admin Portal

The **Admin Portal** is used by administrators to manage the Sophos Firewall.

Administrative access provides highly privileged control over:

* Firewall configuration
* Security policies
* Network settings
* Authentication
* User management
* Device access
* VPN configuration

Because of its privileged nature, administrative access should be protected with MFA.

> [!CAUTION]
> Never treat administrator authentication as equivalent to ordinary user authentication. A compromised firewall administrator account can have significantly greater impact than a compromised standard user account.

---

## 🔌 VPN Portal

The **VPN Portal** provides VPN-related services to users.

Depending on the Sophos Firewall configuration, users may be able to download:

* VPN configuration files
* VPN client software
* VPN setup information
* Other VPN-related resources

Users can use these resources to configure VPN connectivity on their computers.

---

# 🔢 Portal Ports

The demonstration references portal ports such as:

```text
443
444
```

The exact port assignments depend on the Sophos Firewall configuration and may have been changed by the administrator.

> [!NOTE]

Navigate to:

```text
Administration → Device Access
```

to review the configured services and access settings.

# 📱 MFA Enrollment with an Authenticator App

Once MFA is enabled, the user must register an authenticator application.

Common authenticator applications include:

* Google Authenticator
* Microsoft Authenticator
* Other compatible TOTP authenticator applications

The enrollment process generally works as follows:

1. Open the appropriate Sophos Firewall user or VPN portal.
2. Sign in using the assigned username and password.
3. When prompted, begin MFA enrollment.
4. Open the authenticator application on the mobile device.
5. Select the option to add a new account.
6. Scan the QR code presented by the Sophos Firewall.
7. The Sophos account is added to the authenticator application.
8. The application begins generating time-based OTPs.
9. Enter the displayed OTP to complete enrollment.
10. Continue with the login process.

# 🔄 How OTP Authentication Works

After the authenticator is enrolled, the authentication process becomes:

```text
Username
    ↓
Password
    ↓
Authenticator OTP
    ↓
Authentication
    ↓
Access Granted
```

For example:

```text
Username: <username>
Password: <password>
OTP: <6-digit code>
```

The OTP is generated by the authenticator application and periodically changes.

> [!IMPORTANT]
> The OTP is a separate authentication factor. Users must not expect the password itself to satisfy the OTP requirement.

> [!WARNING]
> Never include a real production OTP in documentation, screenshots, support tickets, or training material.

# 🧪 Testing MFA

After configuring MFA, test each applicable access path.

Recommended test sequence:

1. Test the User Portal.
2. Test the VPN Portal.
3. Test remote-access VPN.
4. Test administrative access using an appropriate administrator account.
5. Verify that the authenticator application generates valid OTPs.
6. Confirm that invalid OTPs are rejected.
7. Confirm that users without successful MFA cannot access protected services.
8. Verify that the configuration does not unintentionally lock out users.

---

# ❌ Troubleshooting: "Authentication Failed"

One common issue occurs when MFA is enabled for users who have not completed enrollment.

A user may attempt to connect to the VPN and receive:

```text
Authentication Failed
```

The user may assume that:

* The username is incorrect.
* The password is incorrect.
* There is a spelling mistake.
* The VPN client is malfunctioning.

The user may repeatedly enter the password, which does not resolve the problem.

---

## 🔎 Possible Root Cause

The underlying issue may be that MFA has been enabled but the user has not completed MFA enrollment.

The expected authentication flow is:

```text
Username
   ↓
Password
   ↓
MFA Challenge
   ↓
OTP
   ↓
Authentication
```

But the user may only be completing:

```text
Username
   ↓
Password
```

Therefore, authentication fails.

---

## 🛠️ Recommended Resolution

1. Confirm that MFA is enabled for the user.
2. Confirm that the user has completed MFA enrollment.
3. Verify that the authenticator application is correctly configured.
4. Confirm that the user's device has the correct time.
5. Confirm that the user is entering the current OTP.
6. Test authentication again.

# 🎟️ MFA Token Management

The MFA configuration can display issued authentication tokens associated with users.

When users are enrolled for MFA, their corresponding token information may be visible within the MFA administration interface.

Administrators should periodically review token assignments and remove or revoke tokens that are no longer required, according to organizational procedures.

Review:

* Active MFA tokens
* Users with MFA enabled
* Disabled users with active tokens
* Obsolete tokens
* Tokens associated with departed employees

---

# 📱 Real-World Scenario 7: User Gets a New Mobile Phone

Consider an employee who has MFA configured on their old phone.

The employee receives a new phone and reports:

> "I cannot connect to the VPN because my authenticator is still on my old phone."

The organization should have a documented MFA recovery process.

Depending on the Sophos Firewall configuration and organizational policy, IT may need to:

1. Verify the user's identity.
2. Revoke or disable the old MFA token if necessary.
3. Start the approved MFA recovery or enrollment process.
4. Have the user register the new authenticator.
5. Test VPN authentication.
6. Document the change.

> [!WARNING]
> Never bypass MFA simply because a user has lost their phone. Follow the organization's approved identity-verification and MFA-recovery procedure.

# ⚙️ Device Access and VPN Portal Security

Another important configuration area is:

```text
Administration → Device Access
```

Review the services exposed through the WAN interface.

The VPN Portal should be exposed only when there is a clear operational requirement.

> [!WARNING]
> Avoid unnecessarily exposing management or portal services to the public internet. Services exposed through the WAN interface increase the organization's external attack surface.

If a portal is exposed on a publicly reachable address and port, users may potentially access it using the configured static IP address and port.

For example:

```text
https://<public-ip>:<port>
```

The exact address and port depend on the organization's Sophos Firewall configuration.

---

# 🛡️ Recommended MFA Security Practices

For production environments, consider the following practices:

* Enable MFA for all firewall administrator accounts.
* Enable MFA for remote-access VPN users.
* Protect privileged accounts with MFA.
* Use MFA for user portals where appropriate.
* Communicate MFA changes before enforcement.
* Provide users with enrollment instructions.
* Test MFA with pilot users before organization-wide deployment.
* Maintain a documented recovery process for lost or replaced mobile devices.
* Periodically review MFA tokens and user assignments.
* Minimize services exposed through WAN interfaces.
* Review firewall access policies regularly.
* Keep Sophos Firewall firmware/software appropriately updated.
* Document all MFA-related configuration changes.
* Never ask users to send OTP codes through email or chat.
* Never document real production OTP values.
* Disable access promptly during employee offboarding.

# 📝 Key Takeaways

The most important lessons are:

1. **MFA provides an additional layer of security** beyond the password.
2. **Administrator accounts should be protected with MFA.**
3. **Remote-access VPN users should use MFA.**
4. MFA can be applied to **all users or selected users**, depending on organizational requirements.
5. Users must complete **MFA enrollment** before they can successfully authenticate using MFA.
6. Authenticator applications such as **Google Authenticator** and **Microsoft Authenticator** can be used for OTP generation.
7. MFA should be communicated and deployed carefully to prevent unnecessary user lockouts.
8. **User Portal, VPN Portal, and administrative access are separate services** and should be evaluated individually.
9. WAN-facing services should be minimized and protected according to security requirements.
10. Always test MFA before deploying it to a large remote user population.
11. Maintain a documented recovery process for lost or replaced mobile devices.
12. Review MFA tokens and user assignments periodically.
13. Include MFA in employee onboarding and offboarding procedures.
14. Never share or request OTP values through insecure communication channels.

# 📚 Conclusion

Multi-Factor Authentication is an important security control for Sophos Firewall deployments.

A compromised password should not automatically provide an attacker with access to the organization's firewall, VPN, or internal resources. By requiring an additional authentication factor, organizations can significantly strengthen their authentication security.

For an effective deployment:

> **Protect administrators → Identify users → Plan enrollment → Notify users → Enable MFA → Test → Monitor**

The implementation should always be aligned with the organization's security policies, Sophos Firewall version, authentication architecture, and remote-access requirements.

The firewall configuration is only one part of a successful MFA implementation.

An effective deployment also requires:

* User communication
* Enrollment instructions
* Help Desk procedures
* Lost-device recovery
* Employee offboarding
* MFA token management
* Testing procedures
* Security monitoring
* Documentation

When these components are implemented together, MFA becomes a practical security control rather than simply another firewall setting.
