# Sophos Firewall Disk Space Management, Log Purging, and Troubleshooting

## 📘 Overview

This document covers a practical and important issue that can occur when managing a Sophos Firewall: **disk space exhaustion**.

Imagine that the firewall is operating normally. Users can access the internet, firewall rules and policies are working properly, and the network appears healthy. However, the firewall storage can suddenly become full.

When this happens:

* Reports may no longer be generated properly.
* Logs may no longer be stored.
* The firewall may display an error indicating that a partition is full.
* Troubleshooting information may become unavailable.
* Administrators may need to determine which logs or reports are consuming storage.
* Administrators may need to purge reports or logs through the GUI or CLI.

A typical error message indicates:

> **Partition is full. To clear disk space, click Reports.**

This message indicates that the firewall disk is full and requires immediate attention.

The key questions are:

* Why is the disk space full?
* Which old logs should be deleted?
* Which logs should be retained?
* How can reports be purged from the GUI?
* How can logs be purged from the CLI?
* What should be checked before performing a purge?
* How can repeated disk-space exhaustion be prevented?

This document covers these questions and explains practical procedures for managing Sophos Firewall storage.

---

## ⚠️ Important: Disk Usage Does Not Affect Every Component in the Same Way

Sophos Firewall does not handle a completely full disk in exactly the same way for every component.

For example:

| Component            | Behavior When Storage Is Full                            |
| -------------------- | -------------------------------------------------------- |
| Reports              | Report saving may stop.                                  |
| Event logs           | Older logs may begin to be deleted.                      |
| Troubleshooting logs | Older troubleshooting logs may be compressed or deleted. |

Therefore, a full disk does **not necessarily mean that the firewall will immediately stop operating completely**.

However, a full disk condition must still be resolved as soon as possible.

If troubleshooting logs or audit logs are required later, they may no longer be available. This can become especially important when management requires historical event logs or when an administrator needs evidence for troubleshooting or auditing.

---

# 🔍 Common Causes of Rapid Disk Usage

One common cause of unexpected disk usage is an administrator leaving troubleshooting features enabled after the original problem has been resolved.

Two areas require particular attention:

1. Packet capture
2. Debug mode

---

## Packet Capture

Administrators sometimes start a packet capture while troubleshooting a problem.

For example, an administrator may need to:

* Check logs from a machine.
* Check traffic or hits coming from a machine.
* Capture packets for troubleshooting.

After the issue is resolved, the administrator may forget to stop the packet capture.

This is a common operational mistake.

The problem has already been resolved, but packet capture remains enabled and continues consuming disk space.

### 🔧 Check Packet Capture

If disk usage is increasing suddenly:

1. Open the firewall's diagnostic area.
2. Check whether packet capture is currently enabled.
3. If packet capture is enabled and troubleshooting is complete, stop it.
4. Confirm that packet capture is no longer running.

Sophos also recommends disabling troubleshooting functions after the troubleshooting task is complete so that they do not unnecessarily consume disk space.

---

## Debug Mode

Debug mode is another important troubleshooting feature.

Debug mode is a troubleshooting step that can be enabled from the CLI. When debug mode is enabled, the system starts generating more detailed logs.

The detailed logs are larger than normal logs.

For example, if a specific machine is experiencing a problem and the Sophos technical team remotely accesses the system for troubleshooting, the technical team may access the CLI and enable debug mode.

### ⚠️ Disable Debug Mode After Troubleshooting

After debugging is complete, it is important to disable debug mode.

If the Sophos technical team has remotely accessed the system and enabled debug mode, confirm with them that debug mode has been disabled.

> **Important:** Always cross-check whether debug mode was enabled and confirm that it has been turned off after troubleshooting is completed.

---

# 💾 Understanding the Disk-Full Condition

The firewall's storage can become full because of:

* An administrator's configuration or troubleshooting mistake.
* Packet capture being left enabled.
* Debug mode being left enabled.
* Reports accumulating over time.
* Event logs accumulating over time.
* Troubleshooting logs consuming storage.
* Normal growth of stored data over time.

Regardless of the cause, the immediate requirement is to **free disk space**.

The disk-full error will be resolved only after sufficient disk space becomes available.

# ⚙️ Manage Reports from the GUI

Reports can be managed and manually purged through the Sophos Firewall graphical user interface (GUI).

## Procedure

1. Open the **Reports** section.
2. Select **Show Report Settings**.
3. Review the available report-management options.
4. Before deleting reports, review the configured retention period.

---

## 📋 Review the Log Retention Period

When managing firewall data and disk space, first determine how long reports and logs are being retained.

The **Log Retention Period** displays the retention duration for different types of generated firewall data.

The firewall displays the applicable log types and their configured durations.

In the example discussed in the source material, the retention period is configured for **six months**.

The required retention period can vary according to organizational requirements.

For example:

* Your IT policy may require a longer retention period.
* Your IT security policy may require a shorter retention period.
* Some data may not need to be retained for the currently configured duration.

Where the data is not required for that long, the retention period can be minimized according to organizational policy.

> **Important:** Do not reduce retention periods simply to free disk space. First verify the applicable IT, security, compliance, audit, and organizational requirements.

---

## ⚠️ Report Retention and Event Log Retention Are Different

An important distinction is that the retention setting being discussed for reports does **not necessarily control event-log retention**.

Report retention and event-log retention must therefore be treated as separate concepts.

This section is specifically discussing **reports**.

---

# 🧹 Manually Purge Reports

The report module provides an option to manually purge reports.

You can select:

* Specific report types.
* All applicable reports.
* A custom time period.
* A specific reporting period.

## Procedure

1. Open the **Report** module.
2. Select the report types that you want to purge.
3. Select the required time period.
4. Review the selected data carefully.
5. Perform the manual purge only after confirming that the data can be deleted.

The purge can be customized according to the required report types and time period.

---

## ⚠️ Manual Purge Is an Immediate Action

Manual purge should be treated as an immediate and potentially irreversible operation.

Before performing a purge:

1. Verify organizational requirements.
2. Verify compliance requirements.
3. Verify retention requirements.
4. Verify audit requirements.
5. Verify whether the organization requires historical reports.
6. Obtain the required approval if necessary.
7. Confirm that the data being deleted is no longer required.

For example, if company policy requires accounting reports to be retained for one year, an administrator should not delete those reports without the required approval.

> **Warning:** Once data is purged, recovery may not be possible.

# 📝 Manage Event Logs

Reports and event logs are separate areas of firewall data management.

Event logs provide information about network and security activity.

They can include information such as:

* ISP or network-link status.
* Network activity.
* Link-down and link-up events.
* Security-related events.
* Attack-related events.
* Authentication events.
* Captive Portal user logins.
* Administrator logins.
* Activities performed by administrators after logging in.

Event logs can therefore be important for troubleshooting, security investigations, and auditing.

---

# ⚙️ Event Log Settings

To manage event-log settings:

1. Open **System Services**.
2. Open **Log Settings**.
3. Review the available event-log settings.
4. Review the volume of logs being generated.
5. Configure suppression or external logging where appropriate.

If excessive log storage on the firewall is causing the disk to become full, an external log server can be used.

An example mentioned in the source material is a **Syslog server**.

---

# 🔇 Log Suppression

Sophos Firewall provides log-suppression options for situations where unnecessary high-volume logs are being generated.

## Procedure

1. Open **System Services**.
2. Open **Log Settings**.
3. Locate the log-suppression options.
4. Review the available local-reporting settings.
5. Identify logs that are generating unnecessary volume.
6. Suppress only the logs that are not required.
7. Apply the configuration.

### ⚠️ Do Not Disable Logs Blindly

Do not disable or suppress logs without first understanding their purpose.

Before suppressing a log, confirm that doing so does not conflict with:

* IT security policies.
* Organizational policies.
* Compliance requirements.
* Audit requirements.
* Security monitoring requirements.

If an organization's policy explicitly states that a particular log is not required, that log can be removed or suppressed according to the policy.

# 🛠️ Troubleshooting Logs

Reports, event logs, and troubleshooting logs are different types of data.

They are also not necessarily managed from the same location in the firewall interface.

The firewall interface can therefore appear somewhat complicated because different functions are available in different locations.

---

## Download Troubleshooting Logs from the GUI

Troubleshooting logs can be accessed through the diagnostic tools.

## Procedure

1. Open **Diagnostic Tools**.
2. Scroll down to the troubleshooting-log section.
3. Locate **Troubleshooting Logs**.
4. Select the required log file or files.
5. Download the selected files.

The downloaded troubleshooting logs can then be reviewed locally.

---

## Consolidated Troubleshooting Reports

The diagnostic tools also provide an option for generating and downloading **Consolidated Troubleshooting Reports (CTR)**.

## Procedure

1. Open **Diagnostic Tools**.
2. Locate **Consolidated Troubleshooting Reports**.
3. Generate the required report.
4. Download the report.
5. Store the downloaded report locally for analysis.

After the required troubleshooting data has been downloaded, unnecessary data should not continue consuming firewall disk space.

In that situation, the CLI can be used.

# 🧹 CLI Log Purge

When the requirement is to delete logs completely, the source material provides the following command sequence:

```text
System Diagnostic Purge-
```

The source transcript identifies this as the command used to purge logs.

After entering the command and using the appropriate tab/completion behavior, the source material describes three options:

* `Old Logs`
* `Event Log`
* `All Logs`

If all logs are required to be purged, the source material describes selecting **All Logs**.

> **Note:** The source transcript identifies the command as `Perch`. Verify the exact command spelling and syntax against the Sophos Firewall version and CLI documentation before executing it in production.

---

## ⚠️ Do Not Run a Full Log Purge Blindly

A full log purge is a destructive operation.

Before executing a command that deletes logs:

1. Determine which logs are required.
2. Export required logs.
3. Verify that backups or exports are complete.
4. Confirm retention requirements.
5. Confirm compliance requirements.
6. Confirm audit requirements.
7. Obtain required authorization.
8. Only then perform the purge.

> **Warning:** Required logs should always be exported before deletion when they may be needed for future investigation, auditing, compliance, or security analysis.

# 🔒 Sensitive Log-Deletion Scenarios

The source material also describes a sensitive real-world situation involving requests to remove logs and reports.

In rare cases, senior management or organizational leadership may instruct an administrator to completely clean reports and logs.

In such circumstances, CLI commands may be useful for performing the requested cleanup.

However, log deletion can have significant security, legal, compliance, and audit implications.

---

## Example: Organization-Specific Compliance Requirements

The source material describes a historical example involving a European software-development company.

The organization wanted to create an adult website.

A team was created specifically for this project. The team was placed in a separate area of the floor, with a transparent-glass cabin whose glass was covered.

The systems were dedicated to the project.

The project was worth a significant amount of money, with payment being made in dollars and euros.

The employees working on the project used systems to access examples and reference material for the specific category of content they were developing.

The source material describes activities such as:

* Reviewing examples of category-specific content.
* Looking at references for application development.
* Reviewing competing products or applications.
* Observing buffering behavior and other aspects of the applications.
* Working on the project throughout the day.

The source material states that the activities were legal in the European country involved, while the compliance requirements applicable to the organization in India were different.

After approximately three months, the project was completed.

The project team had changed during the project. For example:

* A junior employee was initially involved.
* Other employees subsequently replaced team members.
* Senior people were hired partway through the project.
* Personnel changed two or three times.

After the project was completed, the administrator was asked to delete everything related to the project.

The source material describes a request to completely clean the relevant information, potentially by representing the situation as a hardware failure so that other clients' activities would not be discovered during an audit.

The concern was that other clients had multiple projects running on the same environment and that sensitive information belonging to other clients could potentially be exposed during an audit.

---

# ⚠️ Security, Legal, Compliance, and Audit Considerations

The example demonstrates why log deletion must never be treated as a simple disk-cleanup activity.

Before making real-time decisions about deleting logs, review:

| Area                 | Question to Consider                                                     |
| -------------------- | ------------------------------------------------------------------------ |
| Log retention policy | What does the organization's retention policy require?                   |
| Compliance           | What compliance requirements apply?                                      |
| Legal requirements   | What legal requirements apply to the data?                               |
| Security policy      | What does the organization's security policy require?                    |
| Audit                | Could the logs be required as audit evidence?                            |
| Authorization        | Has the required management authorization been obtained?                 |
| Data sensitivity     | Could the logs contain sensitive customer or organizational information? |

> **Important:** Log deletion must follow organizational policy, retention requirements, compliance obligations, legal requirements, and security procedures.

The source material notes that unethical requests or activities may sometimes occur. Administrators must therefore understand the consequences of deleting security records and should follow the applicable policies and requirements.

# 📋 Common Operational Mistakes

The source material identifies several common mistakes made by firewall administrators.

## 1. Incorrect Report Retention

Do not retain reports for longer than required without a reason.

Review the report-retention period and configure it according to organizational requirements.

> **Tip:** Keep the retention period as long as required by policy, but do not unnecessarily configure a higher retention period simply because more storage is available.

---

## 2. Leaving Debug Mode Enabled

If debug mode was enabled for troubleshooting:

1. Complete the troubleshooting activity.
2. Disable debug mode.
3. Confirm that detailed logging has stopped.

---

## 3. Leaving Packet Capture Running

Do not leave continuous packet capture enabled after troubleshooting.

After completing packet analysis:

1. Stop packet capture.
2. Confirm that it is no longer running.
3. Monitor disk usage if the capture consumed significant storage.

---

## 4. Storing Excessive Event Logs Locally

If event logs are consuming excessive local storage, consider an external Syslog server where appropriate.

An external logging architecture can provide additional storage for logs.

The source material also mentions that advanced topics may cover how to connect additional servers.

---

## 5. Not Monitoring Disk Usage

Disk usage should be monitored regularly.

A continuously increasing disk-usage trend can be an early warning sign.

# 📊 Monitor Sophos Firewall Disk Usage

To check disk usage:

1. Open **System**.
2. Open **Diagnostic**.
3. Open the **Graph** section.
4. Scroll to the relevant resource information.
5. Review CPU and memory usage.
6. Locate **Disk Usage**.
7. Review current disk utilization.

The disk-usage view can show information such as:

* Temporary files.
* Reports.
* Configuration.
* Signatures.
* Other stored data.

The source material describes the disk-usage information as being displayed visually, including blue indicators.

---

## 📈 Identify Increasing Disk Usage

Monitor disk utilization over time.

If disk usage continuously increases even after cleanup activities, treat this as an early warning sign.

For example:

* Disk usage continues increasing.
* Data is being deleted.
* However, the overall usage trend continues to grow.

This requires further investigation.

Possible areas to investigate include:

* Reports.
* Event logs.
* Troubleshooting logs.
* Packet capture.
* Debug mode.
* Temporary files.
* Other stored firewall data.

If necessary, involve the Sophos technical team for deeper investigation.

---

# ⏱️ Establish a Regular Cleanup and Monitoring Practice

Disk-space management should not be performed only when the firewall reports that the disk is full.

A better operational practice is to monitor usage and understand how quickly data accumulates.

For example, if reports normally need to be purged every:

* Two months
* Four months
* Six months

then review the configured retention period and determine whether it is appropriate for the organization's requirements.

The objective is to prevent disk space from repeatedly reaching a critical level.

---

# 🚨 What to Do When a Disk-Full Error Appears

If the firewall displays a disk-full notification or a similar error:

1. Do not panic.
2. Check current disk utilization.
3. Identify what is consuming storage.
4. Check whether packet capture is enabled.
5. Check whether debug mode is enabled.
6. Review report retention.
7. Review event-log usage.
8. Review troubleshooting logs.
9. Verify organizational retention and compliance requirements.
10. Export any logs that must be retained.
11. Purge only the data that is authorized for deletion.
12. Monitor disk utilization after cleanup.
13. Investigate the root cause if disk usage starts increasing again.

---

# 🔒 Security and Compliance Considerations

Never delete logs simply because they are old without first checking:

* Retention requirements.
* Compliance requirements.
* Legal requirements.
* Security requirements.
* Audit requirements.
* Organizational policies.

> **Warning:** Logs do more than consume disk space. They can also provide important security evidence that may be required during a security incident, investigation, audit, or other critical event.

Deleting logs without checking requirements can permanently remove evidence that may be needed later.

---

# 💡 Best Practices

Use the following practices to reduce the likelihood of repeated disk-space problems:

* Review report-retention requirements regularly.
* Configure retention according to organizational policy.
* Do not retain data longer than necessary.
* Do not blindly disable or suppress event logs.
* Export required logs before performing destructive cleanup.
* Disable debug mode immediately after troubleshooting.
* Stop packet capture when troubleshooting is complete.
* Consider an external Syslog server when additional log storage is required.
* Monitor disk usage regularly.
* Investigate continuously increasing disk utilization.
* Involve the Sophos technical team when the cause cannot be identified.
* Never delete security evidence without verifying retention, compliance, legal, and audit requirements.
* Obtain appropriate authorization before performing destructive log cleanup.

# 📌 Key Takeaways

Sophos Firewall disk-space exhaustion is an operational issue that should be addressed promptly.

The main areas discussed are:

1. **Reports** can consume disk space and may stop being generated when storage becomes full.
2. **Event logs** can consume local storage, and older logs may begin to be removed when the disk is full.
3. **Troubleshooting logs** can also consume storage.
4. **Packet capture** can rapidly consume disk space if it is accidentally left enabled.
5. **Debug mode** generates more detailed logs and should be disabled immediately after troubleshooting.
6. **Report retention** and **event-log retention** should not be treated as the same setting.
7. **Manual report purging** should be performed only after verifying organizational, compliance, and retention requirements.
8. **CLI-based log deletion** is destructive and should not be performed blindly.
9. **Required logs should be exported before deletion**.
10. **External Syslog storage** can be considered when local storage is insufficient.
11. **Disk usage should be monitored regularly**.
12. Continuous disk-growth trends should be investigated as an early warning sign.
13. Logs can provide important **security evidence** and should not be deleted solely because they are old.

The source material concludes that administrators who manage firewalls regularly encounter these types of operational issues.

The main recommendations are:

* Keep report retention only as long as required.

* Do not leave packet capture running continuously.
* Consider external Syslog storage when additional storage is required.
